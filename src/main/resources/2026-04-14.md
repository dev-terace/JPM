# JPM Framework 아키텍처 설계 기획서

## 1. 기존 방식의 문제점

현재 구조는 Java AST로 메서드 바디를 파싱하는 방식으로, 복잡도가 폭발적으로 증가하는 문제가 있다.

```
현재 흐름:
메서드 바디 작성
  → Annotation Processor 기동
  → ClassTree → MethodTree → StatementTree 순회
  → MethodInvocationTree 추출
  → 커맨드 문자열 매칭 ("select", "from", "where" ...)
  → rawArgs 추출 (람다 레퍼런스를 문자열로...)
  → MethodMeta 빌드
```

**핵심 문제:**
- 람다 / 변수 / 삼항연산자 등 패턴 추가될 때마다 파서 수정 필요
- 가독성 최악, 확장성 없음
- 동적 쿼리 표현 불가능

## 2. 새로운 아키텍처 - 역할 분리

### 핵심 원칙

| 레이어 | 담당 | 방식 |
|---|---|---|
| Annotation Processor (컴파일 타임) | Java 파일 생성, 타입 메타 추출 | Java AST (Element API) |
| Runtime (서버 시작) | QueryAST 빌드, XML 생성, 검증 | 리플렉션 + ThreadLocal |

## 3. 컴파일 타임 - Annotation Processor 역할 축소

### 담당하는 것

```
@JpmRepository 스캔
RepoTypeMeta 추출
  - 리턴타입
  - 파라미터타입
  - 컬렉션 여부

생성 파일
  QOrderEntity.java     ← Q클래스 (IDE 자동완성 유지)
  OrderRepository.json  ← 타입 메타 + 소스 해시
```

### 담당하지 않는 것 (제거 대상)

```
제거:
- ClassTree 순회
- MethodTree 파싱
- CompositeParseMemberMethodStep
- ParseMethodBodySteps
- ArgumentTokenExtractor
- DslCommandProcStep
- AstMethodTree
```

### 타입 메타 JSON 구조

```json
{
  "sourceHash": "a3f5c2d...",
  "methods": {
    "findOrders": {
      "returnType": "java.util.List",
      "genericType": "io.jpm.dto.OrderDto",
      "isCollection": true,
      "parameters": [
        { "name": "userId", "type": "java.lang.Long" }
      ]
    }
  }
}
```

> 소스 파일 해시를 컴파일 타임에 심어두는 이유 → 런타임 캐싱에 활용

## 4. 자체 QueryAST - 런타임

### 핵심 개념

Java AST는 언어 구조를 표현하고, 자체 QueryAST는 쿼리 의도를 표현한다.

```
Java AST (sun.source.tree)
    MethodTree
        BlockTree
            MethodInvocationTree  ← 문자열로 커맨드 매칭

자체 QueryAST
    QueryAst
        SelectNode   [line: 10]
        FromNode     [line: 11]
        JoinNode     [line: 12]
        WhereNode    [line: 13]
```

### QueryAST 구조

```java
// AST 루트
public class QueryAst {
    private final String methodName;
    private final String className;
    private final List<QueryNode> nodes;
}

// 노드 계층
public sealed interface QueryNode
    permits SelectNode, FromNode, WhereNode, JoinNode, OrderByNode {
    int lineNumber();  // StackWalker로 캡처
}
```

### 라인 번호 캡처 - StackWalker

```java
public abstract class JpmAbstractQuerySegment {

    public void where(MFieldRef<?, ?> field, String op, Object value) {
        int line = captureCallerLine();
        QueryContextHolder.addNode(new WhereNode(field, op, value, line));
    }

    private int captureCallerLine() {
        return StackWalker.getInstance()
            .walk(frames -> frames
                .filter(f -> !f.getClassName()
                    .equals(JpmAbstractQuerySegment.class.getName()))
                .findFirst()
                .map(StackWalker.StackFrame::getLineNumber)
                .orElse(-1)
            );
    }
}
```

> AST 파싱 방식의 라인 번호와 정확도 동일 (javac가 LineNumberTable을 .class에 포함)

## 5. QueryContextHolder - 메서드별 분리

### ThreadLocal 기반 CTX

```java
public class QueryContextHolder {
    private static final ThreadLocal<Deque<List<QueryNode>>> STACK
        = ThreadLocal.withInitial(ArrayDeque::new);

    public static void init()                  { STACK.get().push(new ArrayList<>()); }
    public static void addNode(QueryNode node) { STACK.get().peek().add(node); }
    public static List<QueryNode> drain()      { return STACK.get().pop(); }
}
```

### 메서드별 분리 흐름

```java
for (Method method : repoClass.getDeclaredMethods()) {
    QueryContextHolder.init();       // 메서드 실행 전 초기화
    method.invoke(repoInstance);     // 이 메서드의 노드만 쌓임
    List<QueryNode> nodes = QueryContextHolder.drain(); // 즉시 수집

    QueryAst ast = new QueryAst(method.getName(), className, nodes);
    repoMeta.addAst(ast);
}
```

> 메서드를 하나씩 순차 실행하기 때문에 ThreadLocal이 섞일 여지 없음
> segment() 중첩 실행 케이스는 Deque 스택 구조로 처리

## 6. XML 생성 - 런타임 (InMemoryResource)

### MyBatis 주입 타이밍

SqlSessionFactory 생성 전에 XML을 InMemoryResource로 주입해야 한다.

```java
@Configuration
public class MyBatisConfig {

    @Bean
    public SqlSessionFactory sqlSessionFactory(
            DataSource dataSource,
            JpmXmlGenerator xmlGenerator) throws Exception {

        SqlSessionFactoryBean factoryBean = new SqlSessionFactoryBean();
        factoryBean.setDataSource(dataSource);
        factoryBean.setMapperLocations(xmlGenerator.generateAll()); // ← 주입

        return factoryBean.getObject();
    }
}
```

### XML 생성 흐름

```
타입 메타 (컴파일 타임 산출물)
    + QueryAST (런타임 빌드)
    ↓
<select id="findOrders"
  resultMap="OrderResultMap"     ← 타입 메타에서
  parameterType="Long">          ← 타입 메타에서
  SELECT o.id, o.status          ← QueryAST에서
  FROM order o                   ← QueryAST에서
  WHERE o.id = #{id}             ← QueryAST에서
</select>
```

## 7. 해시 기반 캐싱

### 캐시 체크 흐름

```
서버 시작
    OrderRepository.json 로드 (sourceHash 포함)
    캐시 파일 존재?
        YES → 해시 동일?
                YES → 캐시 XML 재사용 (메서드 실행 건너뜀)
                NO  → XML 재생성 + 캐시 갱신
        NO  → XML 생성 + 캐시 저장
```

### 캐시 구현

```java
public class XmlCacheStore {
    private static final String CACHE_DIR = "target/jpm-cache/";

    public void save(Class<?> repoClass, String xml, String sourceHash) {
        CachedXml cache = new CachedXml(xml, sourceHash);
        objectMapper.writeValue(
            new File(CACHE_DIR + repoClass.getName() + ".cache"), cache);
    }

    private boolean isCacheValid(Class<?> repoClass, String sourceHash) {
        CachedXml cached = load(repoClass);
        if (cached == null) return false;
        return cached.sourceHash().equals(sourceHash);
    }
}

public record CachedXml(String xml, String sourceHash) {}
```

### 해시 기반으로 확장 가능한 것들

- 변경된 레포지토리만 로그 출력
- 운영 서버 재시작 시간 단축 (캐시 재사용)
- 개발 환경 핫리로드 (파일 변경 감지 후 해당 레포만 재생성)

## 8. 파이프라인 전체 흐름

```
컴파일 타임 (Annotation Processor)
    @JpmRepository 스캔
    타입 메타 추출 + 소스 해시 계산
    → QEntity.java 생성
    → RepoName.json 저장 (타입메타 + 해시)

서버 시작 (Runtime)
    RepoName.json 로드
    해시 비교 → 캐시 유효 여부 판단
    (캐시 미스 시) 메서드 실행 → QueryAST 빌드
    QueryAST 구조 검증 (from 누락, join 조건 등)
    타입 메타 + QueryAST → XML 생성
    XML → InMemoryResource → SqlSessionFactory 주입
    DAO 프록시 생성 → Bean 등록

요청 처리 (Request)
    DAO 프록시 → MyBatis → DB
```

## 9. 검증 레이어

```java
public class QueryValidator {

    public void validate(QueryAst ast) {
        // from() 누락 체크
        if (ast.nodes().stream().noneMatch(n -> n instanceof FromNode)) {
            throw new QueryValidationException(
                "[%s] line %d : from() 누락"
                    .formatted(ast.methodName(), ast.firstNodeLine())
            );
        }
        // join 조건 누락, select 없이 where 등 추가 가능
    }
}
```

> 검증 실패 시 서버 시작 자체를 막음 → 잘못된 쿼리로 서버가 뜨는 일 없음

## 10. 기존 대비 요약

| 항목 | 기존 | 신규 |
|---|---|---|
| 메서드 바디 파싱 | Java AST 직접 파싱 | 메서드 실행으로 대체 |
| 라인 번호 추출 | TreePositionUtil | StackWalker |
| 동적 쿼리 | 불가능 | if/for 자연스럽게 지원 |
| XML 생성 시점 | 컴파일 타임 | 런타임 (SqlSessionFactory 주입 전) |
| 파서 복잡도 | 매우 높음 | 없음 |
| 캐싱 | 없음 | 소스 해시 기반 자동 캐싱 |
| 신규 DSL 추가 | 파서 수정 필수 | 메서드 + 노드 클래스만 추가 |
